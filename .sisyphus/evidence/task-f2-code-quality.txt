--- Issues Found ---

[LOW] R-1: Mutex::lock().unwrap() used 16 times (lines 52,59,67,114,
  123,134,142,163,242,341,374,411,417,436,653,678).
  These only panic if another thread panicked while holding the lock
  (poison). In practice this is safe for this application because:
  - All lock scopes are short (no I/O inside lock)
  - Panic propagation is acceptable for this desktop app
  However, for defense-in-depth, consider:
    .lock().unwrap_or_else(|e| e.into_inner())
  to recover from poisoned mutexes.

[LOW] R-2: app.default_window_icon().unwrap() on line 606.
  If no icon is configured, this panics at startup. The icon is set
  in tauri.conf.json so this is safe in practice but fragile.

[LOW] R-3: eval_webview_script escaping (line 380) only covers
  backtick, backslash, and ${. Does not escape single/double quotes
  in the format!() template. Since the escaped_script is placed inside
  a template literal in the wrapper (line 384), backtick escaping is
  the correct approach. However, if the script contains raw `}})` it
  could break the format!() macro. The risk is low since `{{` and `}}`
  are the Rust escape for literal braces.

--- Bounds Math: PASS with note ---
  Two bounds calculation approaches coexist:

  1. App.svelte recalculateWebviewBounds() [line 47-58]:
     Uses JS constants (SIDEBAR_EXPANDED_WIDTH=250, SIDEBAR_COLLAPSED_WIDTH=60,
     URL_BAR_HEIGHT=50) with window.innerWidth/innerHeight.

  2. Browser.svelte updateWebviewBounds() [line 58-83]:
     Uses DOM measurements via getBoundingClientRect() for sidebar, nav-bar,
     and presets-panel.

  The Browser.svelte approach is more accurate (accounts for presets panel,
  actual DOM sizes). App.svelte's approach is used for animated transitions.
  They agree in steady state because CSS vars match the JS constants.

  Note: The dual approach means a CSS change to sidebar width must be
  updated in TWO places (CSS vars AND App.svelte constants). This is
  documented in the comment on line 19 of App.svelte:
    "// Webview layout constants (must match CSS variables in app.css)"

--- Issues Found ---

[MEDIUM] I-1: Duplicate bounds calculation logic between App.svelte
  (constants-based) and Browser.svelte (DOM-based). If sidebar width
  changes in CSS but not in App.svelte constants, the animated bounds
  during sidebar toggle will be wrong. This is documented but fragile.
  Recommendation: Extract shared constants to a single module or
  derive all values from DOM measurements.

[LOW] I-2: Browser.svelte on_new_window handler (lib.rs:220-231)
  spawns an async task to navigate, but doesn't emit 'browser-url-changed'.
  The on_navigation callback will fire after navigate() completes,
  so this is actually fine - just indirect. No action needed.
