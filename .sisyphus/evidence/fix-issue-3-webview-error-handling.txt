==========================================================
ISSUE #3: WEBVIEW CREATION ERROR HANDLING
==========================================================

ISSUE SUMMARY (from Task F3 Manual QA):
- Severity: MEDIUM
- Description: "Webview creation failures not surfaced to UI"
- User Impact: Silent failures - user clicks Navigate but nothing happens, no error shown
- Root Cause: Frontend sets `browserCreated = true` immediately after async command returns,
  before webview actually exists. If creation fails in spawned Rust task, UI never knows.

----------------------------------------------------------
ROOT CAUSE ANALYSIS
----------------------------------------------------------

**Rust Side (lib.rs:190-256)**:
```rust
#[tauri::command]
async fn create_embedded_browser(app: tauri::AppHandle, url: String) -> Result<(), String> {
    // Spawns async task and returns immediately (line 201)
    tauri::async_runtime::spawn(async move {
        // Actual webview creation happens here (lines 234-238)
        match window.add_child(builder, position, size) {
            Ok(_) => {
                // Updates state and emits success event (lines 240-245)
                app_clone.emit("browser-status", "embedded-open")
            }
            Err(e) => {
                // Logs error and emits failure event (lines 247-249)
                eprintln!("Failed to create embedded browser: {}", e);
                app_clone.emit("browser-status", "error")
            }
        }
    });
    
    Ok(()) // Returns before webview actually created
}
```

**Frontend Side (Browser.svelte:136-156)**:
```typescript
async function handleNavigate() {
    if (!browserCreated) {
        await createEmbeddedBrowser(urlInput); // Returns immediately
        browserCreated = true;  // ❌ Set before webview actually exists!
        showPresets = false;
        // If creation fails in spawned task, browserCreated is wrong
    }
}
```

**KEY INSIGHT**:
- Rust ALREADY emits `browser-status` events with payload "embedded-open" (success) or "error" (failure)
- Frontend had NO LISTENER for these events
- Frontend trusted the command return value instead of waiting for actual creation result

----------------------------------------------------------
SOLUTION IMPLEMENTED
----------------------------------------------------------

**Step 1: Add Status Listener Export (browser.ts)**

Added new export function `listenBrowserStatus()` to complement existing listeners:

```typescript
// browser.ts:102-109 (NEW)
/**
 * Listen for browser status events (creation success/failure).
 * Status values: "embedded-open" (success), "error" (failure)
 */
export async function listenBrowserStatus(callback: (status: string) => void) {
  return listen<string>('browser-status', (event) => {
    callback(event.payload);
  });
}
```

**Step 2: Import New Listener (Browser.svelte)**

Added `listenBrowserStatus` to imports list (line 13).

**Step 3: Add Status Listener Variable (Browser.svelte:32-36)**

```typescript
// Event Listeners
let unlistenUrl: (() => void) | undefined;
let unlistenLoaded: (() => void) | undefined;
let unlistenStatus: (() => void) | undefined; // NEW
```

**Step 4: Wire Up Status Listener (Browser.svelte:111-124)**

Added listener in `onMount()` after existing `listenBrowserPageLoaded`:

```typescript
// Listen for webview creation success/failure
unlistenStatus = await listenBrowserStatus((status: string) => {
  if (status === 'embedded-open') {
    browserCreated = true;      // ✅ Set only when webview actually created
    showPresets = false;
    isLoading = false;
  } else if (status === 'error') {
    browserCreated = false;     // ✅ Reset state on failure
    isLoading = false;
    showToast('Failed to create browser. Please try again.');
  }
});
```

**Step 5: Remove Immediate State Update (Browser.svelte:148-159)**

Changed `handleNavigate()` to let event listener control `browserCreated` state:

```typescript
// BEFORE:
if (!browserCreated) {
    await createEmbeddedBrowser(urlInput);
    browserCreated = true; // ❌ Immediate assignment
    showPresets = false;
}

// AFTER:
if (!browserCreated) {
    // browserCreated will be set by the status listener when creation succeeds
    await createEmbeddedBrowser(urlInput);
    // ... no immediate state change ...
}
```

**Step 6: Clean Up Listener (Browser.svelte:140-144)**

Added cleanup for new listener in `onDestroy()`:

```typescript
onDestroy(() => {
  if (unlistenUrl) unlistenUrl();
  if (unlistenLoaded) unlistenLoaded();
  if (unlistenStatus) unlistenStatus(); // NEW
});
```

EDGE CASES HANDLED
----------------------------------------------------------

1. **User navigates away during creation**:
   - Status event will fire even if user switches pages
   - Listener checks `status` value and updates state appropriately
   - No memory leak: `onDestroy()` cleans up listener

2. **Multiple rapid clicks on Navigate**:
   - `isLoading` flag prevents duplicate `createEmbeddedBrowser()` calls
   - Status listener will only process final successful creation
   - State remains consistent

3. **Webview already exists (persists across page switches)**:
   - Lines 126-138 in `onMount()` check for existing webview via `getEmbeddedUrl()`
   - If found, sets `browserCreated = true` immediately (webview confirmed to exist)
   - Status listener only affects NEW creations

----------------------------------------------------------
TECHNICAL NOTES
----------------------------------------------------------

**Why Rust emits events asynchronously**:
- `window.add_child()` is a heavy operation (creates OS-level window)
- Must run in async task to avoid blocking main thread
- Tauri command returns immediately to prevent IPC timeout
- Events are the idiomatic way to communicate async results back to frontend

**Why we can't make the command synchronous**:
- Would require blocking wait on spawned task
- Blocks Tauri's IPC handler thread
- On Windows, causes deadlock if main thread waits on webview thread
- Async + events is the ONLY safe approach (per Must NOT Have guardrails)

**Alternative approaches considered**:
1. ❌ Poll `getEmbeddedUrl()` after command returns
   - Wasteful (repeated IPC calls)
   - Unreliable timing (how long to poll?)
   - Doesn't surface error messages

2. ❌ Make command return after webview created
   - Violates "No synchronous webview ops" guardrail
   - Causes deadlocks on Windows

3. ✅ Listen for status events (chosen)
   - Leverages existing event infrastructure
   - Clean separation: command initiates, event confirms
   - Provides success/failure details
   - Matches Tauri best practices
