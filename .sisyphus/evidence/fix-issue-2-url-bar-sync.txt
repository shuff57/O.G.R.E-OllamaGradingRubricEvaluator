# Issue #2 Fix: URL Bar Desync After Back/Forward Navigation

**Date**: 2026-02-17 17:01
**Issue**: URL bar doesn't sync after Back/Forward navigation - shows stale URL
**Severity**: Medium (confusing UX, users see wrong URL but webview is correct)
**Status**: ✅ FIXED

---

## Problem Description

From Task F3 verification report:

**Root Cause**:
- Browser.svelte uses two event listeners for URL sync:
  1. `browser-url-changed` (from `on_navigation` callback) - fires BEFORE navigation
  2. `browser-page-loaded` (from `on_page_load` callback) - fires AFTER page loads

- The `on_navigation` callback (lib.rs:211-213) may NOT fire for history API calls
  - `history.back()` and `history.forward()` are in-page navigations
  - Tauri webview `on_navigation` primarily tracks top-level navigations
  - Result: `browser-url-changed` event may not emit for back/forward

- The `on_page_load` callback (lib.rs:215-218) ALWAYS fires after page loads
  - Includes history navigations
  - Emits `browser-page-loaded` with actual URL
  - BUT: Browser.svelte:105-108 only used it for autofill, NOT URL sync

**Example Failure**:
```
User clicks: https://example.com/page1
URL bar: "https://example.com/page1" ✓

User navigates to: https://example.com/page2  
URL bar: "https://example.com/page2" ✓

User clicks Back button (history.back())
Webview: Shows page1 ✓
URL bar: Still shows "https://example.com/page2" ✗ (STALE)
```

---

## Solution Implemented

**Approach**: Add URL bar sync to the `on_page_load` event handler

### Changes Made

**File**: `ogre-desktop/src/pages/Browser.svelte`

**Modified**: Line 105-109 (added URL sync)

**Before**:
```typescript
unlistenLoaded = await listenBrowserPageLoaded(async (url: string) => {
  isLoading = false;
  await tryAutofill(url);
});
```

**After**:
```typescript
unlistenLoaded = await listenBrowserPageLoaded(async (url: string) => {
  isLoading = false;
  urlInput = url; // Sync URL bar with actual webview URL (fixes back/forward desync)
  await tryAutofill(url);
});
```

**Why This Works**:
1. `on_page_load` fires for ALL page loads (including history navigations)
2. Event payload contains the actual webview URL (from `wv.url()`)
3. Updating `urlInput` syncs the URL bar with webview state
4. Redundancy: Both `on_navigation` and `on_page_load` now update URL bar
   - `on_navigation`: Fast update during request (when it fires)
   - `on_page_load`: Guaranteed update after load completes

## Event Flow Analysis

### Normal Navigation (via URL bar or links)

```
User types URL / clicks link
    ↓
on_navigation fires (lib.rs:211-213)
    ↓
emit "browser-url-changed" → urlInput = url ✓
    ↓
Page loads
    ↓
on_page_load fires (lib.rs:215-218)
    ↓
emit "browser-page-loaded" → urlInput = url ✓ (redundant but harmless)
```

**Result**: URL bar syncs twice (no problem, second update is idempotent)

### History Navigation (Back/Forward buttons)

```
User clicks Back/Forward
    ↓
wv.eval("history.back()") or wv.eval("history.forward()")
    ↓
on_navigation MAY NOT FIRE ⚠️
    ↓
(URL bar NOT updated if on_navigation skipped)
    ↓
Page loads from history
    ↓
on_page_load fires (lib.rs:215-218) ✓
    ↓
emit "browser-page-loaded" → urlInput = url ✓ (FIX APPLIED)
```

**Result**: URL bar syncs after page load (fix ensures sync even if on_navigation missed)

## Edge Cases Handled

1. **Rapid navigation**:
   - Multiple `on_page_load` events in quick succession
   - Each updates `urlInput` independently
   - Last event wins (correct behavior)

2. **Failed navigation**:
   - If navigation fails, `on_page_load` doesn't fire
   - URL bar keeps previous URL (correct - webview didn't change)

3. **Redirects**:
   - Server redirects (301, 302)
   - `on_page_load` fires with FINAL URL (after redirect)
   - URL bar shows destination, not intermediate URLs ✓

4. **New window attempts**:
   - `window.open()` calls redirected to same webview (lib.rs:220-229)
   - Treated as normal navigation
   - URL bar syncs via `on_page_load` ✓

5. **External protocol handlers**:
   - `mailto:`, `tel:`, custom protocols
   - Tauri may or may not load these in webview
   - `on_page_load` only fires if webview actually loads
   - URL bar reflects webview state (not broken)

## Alternative Solutions Considered

### Alternative 1: Remove `on_navigation` URL sync
**Approach**: Only use `on_page_load` for URL sync

**Pros**: 
- Eliminates redundant updates
- Single source of truth

**Cons**:
- URL bar updates slightly later (after load vs during request)
- User sees brief stale URL during loading
- **Rejected**: UX regression, redundancy is harmless

### Alternative 2: Add state tracking to prevent redundant updates
**Approach**: Check if `urlInput !== url` before updating

**Pros**:
- Avoids redundant assignments

**Cons**:
- Additional complexity (tracking previous URL)
- Negligible performance benefit
- Edge cases: URL updates with same string but different timing
- **Rejected**: Over-engineering, no real benefit

### Alternative 3: Query webview URL on Back/Forward click
**Approach**: Call `getEmbeddedUrl()` after `eval("history.back()")`

**Pros**:
- Immediate sync without waiting for event

**Cons**:
- Async IPC round-trip (slower than event)
- Timing issues (webview URL may not be updated yet)
- Duplicate logic (events already provide URL)
- **Rejected**: More complex, less reliable

**Selected Solution**: Use existing `on_page_load` event (simplest, most reliable)

## Related Code Paths

### Event Emitters (Rust - lib.rs)

```rust
// on_navigation: Fires BEFORE navigation
.on_navigation(move |url| {
    let _ = emit_nav.emit("browser-url-changed", url.as_str());
    true
})

// on_page_load: Fires AFTER page loads
.on_page_load(move |wv, _payload| {
    if let Ok(url) = wv.url() {
        let _ = emit_load.emit("browser-page-loaded", url.to_string());
    }
})
```
