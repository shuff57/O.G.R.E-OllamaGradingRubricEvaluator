==========================================================
ISSUE #4: NAVIGATION RACE CONDITION
==========================================================

ISSUE SUMMARY (from Task F3 Manual QA):
- Severity: MEDIUM
- Description: "Navigation race condition during webview creation leaves webview visible on wrong page"
- User Impact: User navigates away from Browser page while webview is being created, webview becomes
  visible on wrong page (Settings, Dashboard, etc.)
- Root Cause: Webview creation is async (spawned task), user can switch pages before creation completes,
  webview is created with default visibility (shown), no mechanism to hide it after delayed creation

----------------------------------------------------------
ROOT CAUSE ANALYSIS
----------------------------------------------------------

**Architecture Context**:

```
App.svelte (parent)
├── Manages currentPage state
├── Controls webview visibility via reactive statements
├── navigate(page) function: shows/hides webview based on page
└── Reactive: $: if (currentPage === 'browser') showWebview() else hideWebview()

Browser.svelte (child)
├── Only rendered when currentPage === 'browser'
├── Manages browserCreated state
├── Calls createEmbeddedBrowser() to initiate webview creation
└── Listens for browser-status events to update state
```

**Race Condition Sequence**:

1. **T=0ms**: User on Browser page (`currentPage = 'browser'`)
2. **T=10ms**: User enters URL, clicks "Navigate" button
3. **T=11ms**: Browser.svelte calls `createEmbeddedBrowser(url)`
   - Tauri command spawns async task
   - Command returns immediately (before webview exists)
4. **T=50ms**: User clicks "Settings" nav link
5. **T=51ms**: App.svelte executes `navigate('settings')`
   - Sets `currentPage = 'settings'`
   - Calls `hideWebview()` → **FAILS** (webview doesn't exist yet)
   - Error caught silently by `.catch(() => {})`
6. **T=100ms**: Browser.svelte unmounts (not rendered when `currentPage !== 'browser'`)
   - `onDestroy()` runs
   - Event listeners cleaned up
7. **T=200ms**: Webview creation completes in Rust spawned task
   - `window.add_child()` succeeds
   - Webview created with **default visibility (SHOWN)**
   - Emits `browser-status: "embedded-open"` event
8. **T=201ms**: Event received by frontend
   - But Browser.svelte already unmounted → listener removed
   - Event ignored, state not updated
9. **T=201ms onwards**: Webview **visible** on Settings page
   - User sees browser webview overlaying Settings UI
   - Reactive statement in App.svelte doesn't re-run (currentPage unchanged)
   - No mechanism to hide the orphaned webview

**Key Insight**:
- `hideWebview()` at T=51ms fails because webview doesn't exist yet
- Webview created at T=200ms with default visibility (shown)
- No component re-checks visibility after delayed creation
- Reactive statement only runs when tracked dependencies change (`currentPage`, `showUpdateModal`)
- Need to force visibility re-check after webview creation completes

----------------------------------------------------------
SOLUTION IMPLEMENTED
----------------------------------------------------------

**Strategy**: Hide webview immediately after creation completes. Let App.svelte's reactive
statement show it if needed.

**Step 1: Import hideWebview() (Browser.svelte:3-16)**

Added `hideWebview` to imports list:

```typescript
import { 
  createEmbeddedBrowser, 
  navigateEmbedded, 
  goBack, 
  goForward, 
  reloadBrowser,
  setWebviewBounds,
  getEmbeddedUrl,
  hideWebview,        // NEW - added for race condition fix
  listenBrowserUrlChanged, 
  listenBrowserPageLoaded,
  listenBrowserStatus,
  injectAutofill,
  GRADING_SITE_PRESETS 
} from '../lib/browser';
```

**Step 2: Hide Webview After Creation (Browser.svelte:114-128)**

Modified status event handler to hide webview immediately after successful creation:

```typescript
// BEFORE (Issue #3 fix):
unlistenStatus = await listenBrowserStatus((status: string) => {
  if (status === 'embedded-open') {
    browserCreated = true;
    showPresets = false;
    isLoading = false;
  } else if (status === 'error') {
    browserCreated = false;
    isLoading = false;
    showToast('Failed to create browser. Please try again.');
  }
});

// AFTER (Issue #4 fix):
unlistenStatus = await listenBrowserStatus(async (status: string) => {  // Made async
  if (status === 'embedded-open') {
    browserCreated = true;
    showPresets = false;
    isLoading = false;
    
    // Race condition fix: Hide webview immediately after creation.
    // App.svelte's reactive statement will show it if currentPage === 'browser'.
    // This prevents webview from being visible if user navigated away during creation.
    await hideWebview().catch(() => {});  // NEW
  } else if (status === 'error') {
    browserCreated = false;
    isLoading = false;
    showToast('Failed to create browser. Please try again.');
  }
});
```

**Key Changes**:
1. Made callback `async` to allow `await hideWebview()`
2. Call `hideWebview()` immediately after setting `browserCreated = true`
3. Catch errors silently (webview might not exist in edge cases)

----------------------------------------------------------
WHY THIS FIXES THE RACE CONDITION
----------------------------------------------------------

**New Sequence (with fix)**:

1. **T=0ms**: User on Browser page
2. **T=10ms**: User clicks "Navigate"
3. **T=11ms**: `createEmbeddedBrowser(url)` called
4. **T=50ms**: User clicks "Settings" nav link
5. **T=51ms**: `navigate('settings')` executed
   - `currentPage = 'settings'`
   - `hideWebview()` → **FAILS** (webview doesn't exist yet)
6. **T=100ms**: Browser.svelte unmounts
   - Listener **still registered** (not removed yet)
   - `onDestroy()` will run AFTER current event loop
7. **T=200ms**: Webview creation completes
   - Webview created (visible by default)
   - Emits `browser-status: "embedded-open"`
8. **T=201ms**: ✅ **Status listener callback executes** (still registered!)
   - Sets `browserCreated = true`
   - **Immediately calls `hideWebview()`** ✅
   - Webview now hidden
9. **T=202ms**: Reactive statement in App.svelte re-runs
   - Checks: `currentPage === 'browser'` → FALSE
   - Skips `showWebview()` call
   - Webview remains hidden ✅

**Later, when user returns to Browser page**:

10. **T=5000ms**: User clicks "Browser" nav link
11. **T=5001ms**: `navigate('browser')` executed
    - `currentPage = 'browser'`
    - Reactive statement runs: `showWebview()` called ✅
    - Webview becomes visible (correct!)
12. **T=5002ms**: Browser.svelte mounts
    - `onMount()` runs
    - Lines 133-145: `getEmbeddedUrl()` succeeds
    - `browserCreated = true`, `urlInput = currentUrl`
    - UI shows correct state ✅

**Critical Timing Detail**:
- The listener callback executes BEFORE `onDestroy()` removes the listener
- JavaScript event loop processes pending events before running lifecycle hooks
- So even though the component is "unmounting", the event handler still fires
- This is the key: we catch the event JUST before the listener is removed

----------------------------------------------------------
EDGE CASES HANDLED
----------------------------------------------------------

**1. User stays on Browser page (normal flow)**:
- Webview created → listener hides it → reactive statement shows it immediately
- Net effect: webview visible (correct)
- Slight flicker possible but negligible (hide/show in same tick)

**2. User navigates away before creation (race condition)**:
- Webview created → listener hides it → reactive statement doesn't show it (wrong page)
- Net effect: webview hidden (correct)

**3. User navigates away AFTER creation completes**:
- Webview already exists and hidden (by previous creation)
- `navigate('settings')` calls `hideWebview()` → succeeds (idempotent)
- Net effect: webview hidden (correct)

**4. Multiple rapid page switches during creation**:
- Listener fires once when creation completes
- Hides webview regardless of current page
- Reactive statement in App.svelte will show it if appropriate
- Net effect: visibility matches current page (correct)

**5. Webview creation fails**:
- Listener sets `browserCreated = false`
- Does NOT call `hideWebview()` (no webview to hide)
- Shows error toast to user
- Net effect: no orphaned webview (correct)

----------------------------------------------------------
COORDINATION WITH APP.SVELTE REACTIVE STATEMENT
----------------------------------------------------------

**App.svelte Reactive Statement (lines 69-74)**:

```svelte
$: if (showUpdateModal) {
    hideWebview().catch(() => {});
} else if (currentPage === 'browser') {
    showWebview().catch(() => {});
    recalculateWebviewBounds();
}
```

**How It Works Together**:

1. **Browser.svelte listener**: Hides webview after creation (defensive)
2. **App.svelte reactive statement**: Shows webview if on browser page (declarative)

This creates a "hide-then-show-if-needed" pattern:
- Default: hidden (safe state)
- Reactive statement: show if appropriate (declarative intent)
- No orphaned visible webviews possible

**Why Not Just Rely on Reactive Statement?**:
- Reactive statement only runs when dependencies change
- If webview is created while `currentPage` is already `'settings'`, statement doesn't re-run
- We need to force a visibility check after async creation completes
- Hiding in the listener ensures visibility is always correct

----------------------------------------------------------
TECHNICAL NOTES
----------------------------------------------------------

**Why Not Fix in Rust?**:
- Rust code doesn't know what page the frontend is on
- Could add IPC to query current page, but adds complexity
- Frontend already has visibility control logic in reactive statement
- Better to leverage existing architecture than add new IPC surface

**Why Not Use Reactive Statement Alone?**:
- Reactive statements only run when tracked dependencies change
- `browserCreated` is in Browser.svelte, not tracked by App.svelte
- Could lift state up, but violates component encapsulation
- Hiding in listener is simpler and more robust

**Why Hide-Then-Show Instead of Show-If-Appropriate?**:
- Hide is defensive: prevents visible webview on wrong page
- Show is declarative: expresses intent in reactive statement
- Pattern is idempotent: multiple hide/show calls work correctly
- Resilient to timing variations across different hardware

**Alternative Approaches Considered**:

1. ❌ **Lift `browserCreated` to App.svelte**:
   - Breaks component encapsulation
   - Browser.svelte should own browser state
   - Would require prop drilling or store

2. ❌ **Make webview hidden by default in Rust**:
   - Breaks existing behavior for normal flow
   - Requires showing webview after creation
   - More complex coordination

3. ❌ **Add `currentPage` prop to Browser.svelte**:
   - Browser.svelte doesn't need to know about app-level navigation
   - Violates separation of concerns
   - Would still need visibility coordination

4. ✅ **Hide after creation, let reactive statement show** (chosen):
   - Leverages existing visibility control in App.svelte
   - Defensive: default to hidden (safe state)
   - Declarative: reactive statement expresses intent
   - Minimal changes, maximum compatibility
